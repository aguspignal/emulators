# @emulators/ui

All UI shared by the three emulator apps: screens, React Navigation navigators, theme, components. See the root CLAUDE.md for the monorepo picture.

**React, React Native, navigation libs, `@expo/vector-icons`, the i18n stack (`i18next`, `react-i18next`, `intl-pluralrules`), and Expo native modules the shared UI needs (`expo-sqlite`, `expo-keep-awake`, `expo-haptics`, `expo-localization`) are peerDependencies — never move them to `dependencies`.** The apps own the real installed versions (kept SDK-compatible via `npx expo install` in each app), and adding a new Expo native module here means `npx expo install` in all three apps plus a rebuild — autolinking only sees an app's own `node_modules`. The only regular dependencies allowed are `@emulators/core-interface` and `@emulators/storage`.

## Structure

- `src/AppRoot.tsx` — shared root: `ErrorBoundary` (outermost — one boundary covers all three apps) + `SafeAreaProvider` + `SQLiteProvider` (opens the library DB, runs `migrate`) + `SettingsProvider` + `NavigationContainer` + `RootNavigator`. Apps render `<AppRoot config={...} />`. A DB open/migrate failure swaps the provider for `ErrorState` with a retry that remounts it; expo-sqlite calls `onError` **during render**, so the handler defers its setState with `queueMicrotask` — keep that.
- `src/config.tsx` — `AppConfig` (console specs, `core`, `EmulatorView`, `licenseNotice`) + `useAppConfig()`. This is the only channel for per-app differences; screens must not know which app they're in. `licenseNotice` is deliberately **required**, not optional like `coverIndexes`: every app vendors an emulator core whose licence obliges us to point the user at its source, so the type system is what stops a new app shipping without one.
- `src/navigation/` — native-stack `RootNavigator` and the typed `RootStackParamList`: `Home`; `Emulator { romId, romUri }` (`romUri` is derived at navigation time via `romFileUri()`, never persisted); `Settings`; `License` and `Help` (no params); `Language`; `Controls`. Home's `headerRight` — the info icon that opens `Help` and, to its right, the gear that opens `Settings` — is declared in the navigator's `options` callback, not by the screen: it depends on nothing `HomeScreen` holds, so there is no `setOptions` effect to keep in sync. The navigator calls `useTranslation()` so screen titles retitle live on a language change. Orientation is per screen and stated explicitly on every screen — `Emulator` and `Controls` are `all` (full sensor, so a game follows the phone even with the system rotation lock on), the rest are `portrait_up` — because react-native-screens resets the activity to *unspecified*, not the manifest's `portrait`, when an orientation-setting screen pops.
- `src/screens/`:
  - `HomeScreen` — the ROM library: poster grid, import (file picker, folder picker, or open-with via `useOpenedRom` + `importRomFromUri`), favorite/delete, boot-on-tap. Delete is DB-row-first-then-file: a partial failure strands at worst an orphan file, never an undeletable entry.
  - `SettingsScreen` — General (language, haptics, About) and Legal sections. The Terms/Privacy `BrowserRow`s render inert while an app leaves `termsUrl`/`privacyUrl` unset. Row types differ on purpose: `open-outline` leaves the app, `chevron-forward` stays in it.
  - `LanguageScreen` — an Automatic row plus the endonyms from `LANGUAGES`. Picking calls `setLanguage` and stays put — the instant retranslation is the confirmation.
  - `ControlsScreen` — pad size and opacity, dragged over a live full-size preview. Headerless and `orientation: "all"`, mirroring `Emulator`, because it previews through the same `useEmulatorLayout` call the game uses: a header would take the height that makes the preview true. It edits whichever orientation the device is held in (rotating switches sides — drafts are held for both and seeded once, so one orientation can never overwrite the other) and draws with `PadVisuals` alone, never `GamepadOverlay`, so the editor cannot reach `core` or press a button. Sliders preview on every frame and persist only on release. The settings panel is centred in the *game area* in portrait (the pad's Select/Menu/Start row sits at the band's top edge, so a window-centred panel lands on it) and in the whole window in landscape, where the centre is the one region free of buttons.
  - `HelpScreen` — the import guide. Step copy interpolates the `home.*` button labels instead of repeating the words, so a re-worded button can't desync the guide; accepted extensions come from `acceptedExtensions(consoles)`.
  - `LicenseScreen` — renders `AppConfig.licenseNotice` (blank lines → paragraphs, bare URLs → links). Bundled, never fetched: it satisfies the core's source-availability clause, so it must be readable offline and describe the shipped binary.
  - `EmulatorScreen` — hosts the native `EmulatorView`; owns boot/unload, layout (`useEmulatorLayout`) and saving. Gotchas: `applyRomInfo` is log-only — a failed DB write must never eject a running game; the core `error` event is subscribed only **after** a successful boot — load failures also reject, and an earlier subscription double-alerts; the `AppState` pause resumes only if the core was *running* at that moment — a game paused behind the menu never resumes hidden; the pad is laid out from `CONSOLES[RomInfo.console]` (the console the core read from the header, not `consoles[0]`) — a Game Boy ROM in the GBA app shows no L/R; `recordState` is the one save path — `core.saveState` + thumbnail + `save_states` row + removal of the slot's previous thumbnail.
- `src/components/gamepad/` — the on-screen pad.
  - `layout.ts` and `hitTest.ts` — pure, no React: `buildEmulatorLayout` splits the window between the emulator view and the pad for the current orientation, `buildGamepadLayout` fills a given rect with absolute-coordinate regions for a `ConsoleSpec`'s `buttons`, `hitTest.ts` resolves a touch point to buttons (the D-pad uses eight equal octants, so corners give true diagonals). `useEmulatorLayout.ts` is the React binding (window dimensions + insets).
  - `GamepadOverlay.tsx` — the responder layer, and only that. It takes a prebuilt `GamepadLayout`, it does not build one.
  - `PadVisuals.tsx` — the drawing: the fill/border colours, `RegionView`, `DpadView`. No responder, no core, no state, which is what lets the settings editor preview a pad it cannot press. The `opacity` prop lands on this inner view rather than on `GamepadOverlay`'s root, so the responder keeps an alpha of 1 and is never composited off-screen; `pointerEvents="none"` passes touches straight through, and hit-testing is arithmetic against rects, so how faint the pad is drawn can never reach input.
  - `GameMenu.tsx` — the pause menu: a full-screen layer showing the library display name (the `romName` route param) over icon rows — Resume / Save / Load / Mute and Speed-up (switch rows: the whole row is the pressable and the `Switch` is `pointerEvents="none"` display-only; the screen owns both states and drives `core.setVolume(0|1)` / `core.setSpeed(2|1)`, re-applying them on boot because the native audio sink and frame pacing outlive the ROM) / a cheats stub (alerts "Not available yet") / Reset (confirms first) / Auto save and exit. While any menu layer is up, hardware back peels it instead of popping the screen.
  - `SlotSheet.tsx` — the slot picker Save/Load open: thumbnail + relative time per slot, long-press to delete; slot 0 appears as "Auto" when loading and never when saving. Built from `SecondaryButton.tsx`.
- `src/i18n/` — the whole translation setup: `index.ts` initializes the default i18next instance at module scope (synchronous — `initAsync: false`, bundled catalogs, `intl-pluralrules` polyfill first because Hermes lacks `Intl.PluralRules`), resolving the startup language from `expo-localization`'s `getLocales()` by **bare language code** (es-ES → the es-419 catalog, pt-PT → pt-BR, zh-Hant → zh-Hans) with English as `fallbackLng`. `locales/*.ts` are the ten catalogs (`.ts`, not `.json` — the base tsconfig has no `resolveJsonModule`); `en.ts` is the reference shape and `i18next.d.ts` feeds it to `t()`'s types, so key typos fail `npm run typecheck`; the other nine may differ only in plural suffixes (ru carries one/few/many). `LANGUAGES` (code + endonym) is the single supported-language list. Because `initReactI18next` registers the default instance there is no provider — which is what lets `ErrorBoundary` and the pre-SQLite db-error `ErrorState` translate.
- `src/settings/SettingsContext.tsx` — `SettingsProvider` + `useSettings()`: app settings read once from the SQLite `settings` table into React state, written back fire-and-forget. Settings: `hapticsEnabled` (default on; a missing row keeps the default, so defaults change in code without a migration), `language` (`'auto'` or a supported code; `'auto'`, a missing row, and an unknown value all mean "follow the device"), and `padScale`/`padOpacity` — the gamepad's size and transparency, one value per orientation, since the landscape pad floats over the game while the portrait one has its own band. Their ranges, `settings` keys and `parseStored` (null, `NaN` and out-of-range all fall back to the default) live in `settings/padCustomization.ts`, which is pure and React-free. The language load gates `children` on `null` until the stored override has been applied via `i18n.changeLanguage` — otherwise an override flashes the device language on every cold start — and the gate opens in `finally`, so a failed read can never hold the app. `GamepadOverlay` consumes haptics — one `expo-haptics` `Virtual_Key` tick per event that presses a new button (never per button, so a diagonal is one buzz; sliding onto a new D-pad arm ticks too), plus one for the menu region.
- `src/storage/useRoms.ts` — the one React hook over `@emulators/storage` (kept here so that package stays React-free). Re-queries on focus; exposes `error`, and `reload` **never rejects** — callers may fire-and-forget it.
- `src/storage/useOpenedRom.ts` — hands `HomeScreen` the URI of a ROM the system asked the app to open (a file manager's "open with"). React Native's `Linking` covers both delivery paths with no native code: `getInitialURL()` returns the launch intent's data on a cold start, and the `url` event fires from `onNewIntent` while the app runs. **Deliberately RN's `Linking`, not `expo-linking`** — that would be a new peerDependency (install ×3) for a wrapper on the same module. The hook filters to `content://` and `file://` because the app's own `gba://` deep links arrive through the very same channel, and de-dupes by URI since a cold start and the event can both deliver one.
- `src/storage/useCoverSweep.ts` — fills in missing cover art on Home focus, on import, and on pull-to-refresh. Its candidates come from the database, never from the `roms` array a caller passes in; that decoupling is what makes it safe to hand `reload` as `onChanged` without a render loop.
- `src/components/` — `RomTile` (the library grid poster) and `posterGrid.ts` (pure column/width maths, like the gamepad's `layout.ts`), `EmptyLibrary`, `PrimaryButton`, `Slider` (hand-rolled on the responder API — no dependency and no rebuild; `onChange` per frame, `onCommit` on release, which is where a persist belongs. It uses `locationX`, which does **not** contradict the pad's `pageX` rule: that rule is about comparing several fingers across target views, while this is one finger on one view whose children are all `pointerEvents="none"`), `ImportProgress` (the folder-import overlay: a transparent `Modal` with `onRequestClose` deliberately a no-op, so Android back can't dismiss it mid-copy — there is no cancel, because a batch stopped part-way leaves a library the summary can't describe), `Dialog` (the themed stand-in for `Alert.alert`: same title/message/buttons shape, one transparent `Modal`, ≤2 buttons in a row and 3+ stacked so an option list and a confirm share one component. Purely presentational — the component raising it owns the `useState` and renders its own copy, which is why a `Dialog` inside `GameMenu`/`SlotSheet` still draws above them: a `Modal` is its own window, not a view in the tree. That window also swallows the back key, so `EmulatorScreen`'s menu-peeling `BackHandler` never sees it), `ErrorState` (full-screen fallback — deliberately context-free with its own background so it renders even when the providers above it are broken), `ErrorBoundary`.
- `src/utils/` — `format.ts` (`formatBytes`, plus `formatLastPlayed`/`formatRelativeTime`, which translate through `time.*` keys with `{{count}}` plurals and pass `i18n.language` to `toLocaleDateString`); `errors.ts` (`showErrorAlert` — logs the raw error, alerts safe copy; maps a `RomImportError`'s `code`/`params` to the localized `import.*` message).
- `src/theme/` — colors, radius, spacing, `fonts` (the two family names) and `typography` (the four text tokens, each already carrying its `fontFamily`).
- `assets/fonts/` — the bundled `.ttf`s (Tourney Black, Roboto Regular/SemiBold) plus each family's OFL text. One copy for three apps, kept here because the theme that names them is here — but they are **registered by each app's `app.json`**, not by this package.

## Rules

- Never import from `apps/*` — the dependency arrow points the other way.
- **User-facing strings come from the i18n catalogs, never inline.** Function components that render text use `useTranslation()` — its `t` changes identity on a language switch, which is the re-render signal, so `t` belongs in the dep array of any `useMemo`/`useCallback` that calls it (HomeScreen's `sections` memo, or section titles go stale). Non-reactive code — `ErrorBoundary` (class), `utils/errors.ts`, `utils/format.ts`, module-level handlers — uses the global `i18n.t`, evaluated at call time. **All of `EmulatorScreen` uses global `i18n.t` deliberately**: a hook `t` in its callback deps would re-run the boot effect on a language change and reboot the running game. Console display names and abbreviations, the license notice, and gamepad glyphs stay untranslated on purpose; the Home header is `home.title`, a translated pattern around the console abbreviations joined from `AppConfig.consoles`. A new catalog key goes into `en.ts` first (that's what types `t()`) and then into all nine other locales — same keys, only plural suffixes may differ.
- **Two type tiers, and a translated sentence never gets the display one.** `typography.title` and `typography.button` are Tourney Black (`fonts.display`) — headings and short labels; `typography.body` and `typography.caption` are Roboto (`fonts.body`) — everything read in sentences. Tourney is **Latin-only** (no Cyrillic, Greek or CJK), so putting a translated sentence on `fonts.display` drops the whole Russian or Japanese string to Android's per-glyph system fallback. Tourney is registered at 900 and nothing else; Roboto at 400 and 600 only. Both families are embedded at build time by the `expo-font` plugin entry in **each app's `app.json`**, so adding a weight or a family means editing all three and rebuilding — a Metro reload against an old binary shows the font silently missing. `"Roboto"` deliberately shadows Android's built-in: `ReactFontManager` checks its custom-font cache first, which is how the app beats OEM font substitution.
- **The gamepad must stay one responder view.** React Native allows a single responder at a time, so a `Pressable` per button cannot register the D-pad and A together — `GamepadOverlay` claims the responder once and hit-tests every entry in `nativeEvent.touches` itself. For the same reason the menu button is a *region* in that overlay, not a sibling `Pressable`, and the pause menu only works because the overlay is `suspended` (which also releases everything held). Use touch `pageX`/`pageY`, never `locationX`/`locationY` — the latter are relative to each touch's own target view and cannot be compared across fingers. `buildGamepadLayout` appends the loosely-bounded D-pad last because `hitRegion` returns the first match.
- **Pad scale saturates; it is never clamped to the worst device.** `padMetrics(area, buttons, scale)` evaluates the whole size block at a candidate scale and reports whether it fits — the top stack clearing the D-pad/face cluster, the D-pad and cluster clearing each other along the bottom, ZL/ZR clearing each other in the middle. `buildGamepadLayout` steps down by 0.02 until it fits, with a floor of `min(requested, 1)`: at or below the stock size the request is always honoured exactly, which is what keeps scale 1 byte-identical to the pad that shipped before the setting existed. Portrait growth is bound by the band's *width*, not its height, so phones typically saturate near 1.05–1.2× while landscape reaches the top of the range. `fittingScale(options)` runs the same step-down without building a layout; `ControlsScreen` calls it with `PAD_SCALE.max` and makes the result (snapped down to the slider's step) its size slider's `max`, so the slider and the pad run out of room together instead of the slider travelling past a pad that has stopped growing. `margin`, `smallGap` and `HIT_SLOP` deliberately do not scale — buttons stay pinned to the area's edges and grow inward, and touch slop tracks the size of a finger.
- **`padScale`/`padOpacity` must stay memoized in `SettingsContext`.** They are `Record`s built inside the provider's `useMemo`, never inline in a consumer: a fresh object per render would change `useEmulatorLayout`'s memo input every render, and `GamepadOverlay` calls `releaseAll()` on every `layout` identity change — the pad would drop whatever the player is holding, constantly. `useEmulatorLayout` additionally depends on `scale.portrait`/`scale.landscape` as primitives, so identity churn cannot reach it even if this rule is later broken.
- **Nothing under `src/` may import `expo-file-system`.** Every filesystem and network call lives in `@emulators/storage`; this package receives a `coverUri(...)` string and calls a hook. A new import of it here means the design has gone wrong.
- **The library is a poster grid, built as a SectionList of rows.** `posterGridLayout(windowWidth)` gives the column count and `chunkRows` slices the ROMs into rows the list renders one at a time — not `numColumns`, which can't span the favourites/rest split. Favourites only become their own section once one exists; "My games" carries its title either way. Empty libraries must produce **zero** sections, not one empty one, or `ListEmptyComponent` never renders (SectionList counts a section's header and footer as items). The add button lives in `ListHeaderComponent` and is rendered only when the library is non-empty — SectionList draws the list header *and* the empty component together, and `EmptyLibrary` already has its own. Tiles get a fixed pixel width rather than `flex: 1`, so a final row of one doesn't stretch across the screen. Size and last-played moved from the row into the long-press alert.
- **Icons come from `@expo/vector-icons`, never from a Unicode glyph.** It is installed in all three apps and is a peerDependency here. Import the family directly (`@expo/vector-icons/Ionicons`) so Metro doesn't pull every font set into the bundle. It needs no rebuild — it is JS plus font assets, and `expo-font` already ships inside `expo`.
- Anything console-specific (screen count, aspect ratios, touch screen) comes from `ConsoleSpec` data in `@emulators/core-interface`, not from conditionals on the app.
- **The emulator screen must work in both orientations.** Landscape floats the pad over a full-bleed game; portrait gives the game the top and the pad a band below. One `buildEmulatorLayout(spec, …)` call decides both the native view's rect and the pad's, so they can't disagree — never place either from its own measurement. Native views aspect-fit whatever rect they're handed; a multi-screen console additionally re-arranges with the device — `EmulatorScreen` sends the view a `screenLayout` prop (`"horizontal"` in landscape, `"vertical"` otherwise) and `touchScreenRect` takes the same orientation, so the native compositor and the touch mapping can't disagree. The portrait band gives height back — down to `PORTRAIT_PAD_MIN_PX`, never below, and never growing — when the console's composited frame (`stackedFrame`) is too tall to fill the game area's width, which is what would otherwise letterbox the DS stack into black side gaps. Rotation is pure JS re-layout: the Android activity declares `configChanges="orientation|screenSize"`, so it is never recreated and the emulation thread never restarts.
- **The exit save must block the pop, and must never trap the player.** `EmulatorScreen` intercepts `beforeRemove`, saves the automatic slot, and only then re-dispatches the action — unmounting unloads the core, so a save still in flight would be lost. That `finally` is not optional: if the save throws, the screen still has to close. A guard ref lets the re-dispatched action through, and the interception is skipped entirely before the game has booted, or the boot-failure alert's `goBack()` would soft-lock the screen. Backgrounding saves the same slot fire-and-forget (nothing is unloading), because Android can kill the process without further warning.
- **Auto-resume failures are silent.** A slot-0 state that won't load costs the player their position, not their game; log it and boot fresh. Never alert — the alert would reappear on every attempt to open that ROM.
- User-facing failures go through `showErrorAlert` (alerts) or `ErrorState` (full-screen states) — never a hand-rolled `Alert.alert` with raw error text. Only `RomImportError` messages are written for users; anything else (native, SQLite, FS) can leak internals like absolute paths. Everything that is *not* a failure — confirms, option lists, notices — uses `Dialog`, never `Alert.alert`. `showErrorAlert` is still the system alert because it is called from module scope (`utils/links.ts`, all of `EmulatorScreen`) where no component holds the state a `Dialog` needs.
- Android is the only target; don't add `Platform.OS === 'ios'`/web branches.
- Ships raw TS/TSX (`main: src/index.ts`), no build step; Metro compiles it. New public exports go through `src/index.ts` (which also re-exports `@emulators/storage` so apps have one import surface). Verify with `npm run typecheck`.
