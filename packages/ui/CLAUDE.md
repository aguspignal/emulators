# @emulators/ui

All UI shared by the three emulator apps: screens, React Navigation navigators, theme, components. See the root CLAUDE.md for the monorepo picture.

**React, React Native, navigation libs, and Expo native modules the shared UI needs (`expo-sqlite`, `expo-keep-awake`) are peerDependencies — never move them to `dependencies`.** The apps own the real installed versions (kept SDK-compatible via `npx expo install` in each app), and adding a new Expo native module here means `npx expo install` in all three apps plus a rebuild — autolinking only sees an app's own `node_modules`. The only regular dependencies allowed are `@emulators/core-interface` and `@emulators/storage`.

## Structure

- `src/AppRoot.tsx` — shared root: `ErrorBoundary` (outermost — one boundary covers all three apps) + `SafeAreaProvider` + `SQLiteProvider` (opens the library DB, runs `migrate`) + `NavigationContainer` + `RootNavigator`. Apps render `<AppRoot config={...} />`. A DB open/migrate failure swaps the provider for `ErrorState` with a retry that remounts it; expo-sqlite calls `onError` **during render**, so the handler defers its setState with `queueMicrotask` — keep that.
- `src/config.tsx` — `AppConfig` (app name, console specs, `core`, `EmulatorView`) + `useAppConfig()`. This is the only channel for per-app differences; screens must not know which app they're in.
- `src/navigation/` — native-stack `RootNavigator` and the typed `RootStackParamList` (`Home`, `Emulator { romId, romUri }` — `romUri` is derived at navigation time via `romFileUri()`, never persisted). Orientation is per screen: `Home` is `portrait_up`, `Emulator` is `all` (full sensor, so a game follows the phone even with the system rotation lock on). Both are stated explicitly — react-native-screens resets the activity to *unspecified*, not to the manifest's `portrait`, when an orientation-setting screen pops.
- `src/screens/` — `HomeScreen` (the ROM library: list, import, favorite/delete, boot-on-tap; delete is DB-row-first-then-file, so a partial failure strands at worst a harmless orphan file, never an undeletable entry) and `EmulatorScreen` (hosts the app's native `EmulatorView`, loads/unloads the ROM, reconciles `RomInfo` into the DB via `applyRomInfo` — log-only, a failed DB write must never eject a running game; subscribes to the core `error` event only **after** a successful boot, because load failures also reject and an earlier subscription double-alerts; holds `useKeepAwake()`, pauses the core whenever `AppState` leaves `active` and resumes only if the core was *running* at that moment — so a game paused behind the menu never resumes hidden, and a real core is still expected to enforce this natively; renders the gamepad + pause menu once booted, laying the pad out from `CONSOLES[RomInfo.console]` — the console the core read from the header, not `consoles[0]`, so a Game Boy ROM in the GBA app shows no L/R; owns the orientation split via `useEmulatorLayout`, positioning the native view absolutely from `layout.screen` and painting the portrait pad band behind the pad; and owns saving — `recordState` is the one path that follows a `core.saveState` with a thumbnail, a `save_states` row, and the removal of that slot's previous thumbnail).
- `src/components/gamepad/` — the on-screen pad. `layout.ts` and `hitTest.ts` are pure (no React): `buildEmulatorLayout` splits the window between the emulator view and the pad for the current orientation, `buildGamepadLayout` fills a given rect with absolute-coordinate regions for a `ConsoleSpec`'s `buttons`, `hitTest.ts` resolves a touch point to buttons (the D-pad uses eight equal octants, so corners give true diagonals). `useEmulatorLayout.ts` is the React binding (window dimensions + insets). `GamepadOverlay.tsx` is the responder layer — it takes a prebuilt `GamepadLayout`, it does not build one; `GameMenu.tsx` is the pause menu (Resume / Save state / Load state / Reset / Exit) and `SlotSheet.tsx` the slot picker it opens (thumbnail + relative time per slot, long-press to delete; slot 0 appears as "Auto" when loading and never when saving). Both are built from `SecondaryButton.tsx`.
- `src/storage/useRoms.ts` — the one React hook over `@emulators/storage` (kept here so that package stays React-free). Re-queries on focus; exposes `error`, and `reload` **never rejects** — callers may fire-and-forget it.
- `src/storage/useCoverSweep.ts` — fills in missing cover art on Home focus, on import, and on pull-to-refresh. Its candidates come from the database, never from the `roms` array a caller passes in; that decoupling is what makes it safe to hand `reload` as `onChanged` without a render loop.
- `src/components/` — `RomTile` (the library grid poster) and `posterGrid.ts` (pure column/width maths, like the gamepad's `layout.ts`), `RomListItem` (the pre-grid row; no longer rendered anywhere, kept only because it is a published export), `EmptyLibrary`, `PrimaryButton`, `ErrorState` (full-screen fallback — deliberately context-free with its own background so it renders even when the providers above it are broken), `ErrorBoundary`.
- `src/utils/` — `format.ts` (`formatBytes`, `formatLastPlayed`); `errors.ts` (`showErrorAlert` — logs the raw error, alerts safe copy).
- `src/theme/` — colors, radius, spacing, typography.

## Rules

- Never import from `apps/*` — the dependency arrow points the other way.
- **The gamepad must stay one responder view.** React Native allows a single responder at a time, so a `Pressable` per button cannot register the D-pad and A together — `GamepadOverlay` claims the responder once and hit-tests every entry in `nativeEvent.touches` itself. For the same reason the menu button is a *region* in that overlay, not a sibling `Pressable`, and the pause menu only works because the overlay is `suspended` (which also releases everything held). Use touch `pageX`/`pageY`, never `locationX`/`locationY` — the latter are relative to each touch's own target view and cannot be compared across fingers. `buildGamepadLayout` appends the loosely-bounded D-pad last because `hitRegion` returns the first match.
- **Nothing under `src/` may import `expo-file-system`.** Every filesystem and network call lives in `@emulators/storage`; this package receives a `coverUri(...)` string and calls a hook. A new import of it here means the design has gone wrong — and it would need a new peerDependency plus `npx expo install` in all three apps.
- **The library is a poster grid, built as a SectionList of rows.** `posterGridLayout(windowWidth)` gives the column count and `chunkRows` slices the ROMs into rows the list renders one at a time — not `numColumns`, which can't span the favourites/rest split. Favourites only become their own section once one exists; with none, a single untitled section keeps the plain grid. Empty libraries must produce **zero** sections, not one empty one, or `ListEmptyComponent` never renders (SectionList counts a section's header and footer as items). Tiles get a fixed pixel width rather than `flex: 1`, so a final row of one doesn't stretch across the screen. Size and last-played moved from the row into the long-press alert.
- Anything console-specific (screen count, aspect ratios, touch screen) comes from `ConsoleSpec` data in `@emulators/core-interface`, not from conditionals on the app.
- **The emulator screen must work in both orientations.** Landscape floats the pad over a full-bleed game; portrait gives the game the top and the pad a band below. One `buildEmulatorLayout` call decides both the native view's rect and the pad's, so they can't disagree — never place either from its own measurement. Native views aspect-fit whatever rect they're handed, so no layout code needs the console's pixel dimensions. Rotation is pure JS re-layout: the Android activity declares `configChanges="orientation|screenSize"`, so it is never recreated and the emulation thread never restarts.
- **The exit save must block the pop, and must never trap the player.** `EmulatorScreen` intercepts `beforeRemove`, saves the automatic slot, and only then re-dispatches the action — unmounting unloads the core, so a save still in flight would be lost. That `finally` is not optional: if the save throws, the screen still has to close. A guard ref lets the re-dispatched action through, and the interception is skipped entirely before the game has booted, or the boot-failure alert's `goBack()` would soft-lock the screen. Backgrounding saves the same slot fire-and-forget (nothing is unloading), because Android can kill the process without further warning.
- **Auto-resume failures are silent.** A slot-0 state that won't load costs the player their position, not their game; log it and boot fresh. Never alert — the alert would reappear on every attempt to open that ROM.
- User-facing failures go through `showErrorAlert` (alerts) or `ErrorState` (full-screen states) — never a hand-rolled `Alert.alert` with raw error text. Only `RomImportError` messages are written for users; anything else (native, SQLite, FS) can leak internals like absolute paths.
- Android is the only target; don't add `Platform.OS === 'ios'`/web branches.
- Ships raw TS/TSX (`main: src/index.ts`), no build step; Metro compiles it. New public exports go through `src/index.ts` (which also re-exports `@emulators/storage` so apps have one import surface). Verify with `npm run typecheck`.
