# apps/gba — GBA Emulator

Android-only Expo app emulating Game Boy, Game Boy Color, and Game Boy Advance via the **mGBA** core (C, integrated over JNI). See the root CLAUDE.md for monorepo-wide rules and the shared app commands.

- Android package: `com.aguspignal.gba` · slug `gba` · display name "GBA Emulator" (placeholder, changeable in `app.json`).
- `app.json` → `android.intentFilters` is what puts the app in Android's "Open with" list for ROM files. Android matches `ACTION_VIEW` on **MIME type**, and `.gba`/`.gbc`/`.gb` have none registered, so a `content://` filter is the only kind that works — but it takes **two** of them, and dropping either loses a whole class of file manager:
  - `scheme: content` + `mimeType: application/*` — a DocumentsProvider-backed picker sends `application/octet-stream` (MediaStore records unknown extensions as octet-stream), but a *downloaded* file keeps whatever `Content-Type` the server sent, forwarded verbatim when tapped in Downloads — nonstandard subtypes like `application/x-download` are common, and one nothing on the phone claims hits "no apps can open this file". The wildcard covers all of it while still not claiming `image/video/audio/text`, so the noise stays bounded.
  - `scheme: content` with **no `mimeType` at all** — matches senders that build the intent with a **null** type when their own extension→MIME table misses. A filter with no `mimeType` matches *only* typeless intents, so the two don't overlap and neither is redundant. **It cannot rescue Samsung My Files' tap**, though: verified on One UI (SM-A566E), My Files logs `getMimeType() ] unsupported file type extension : gba, mimeType :` and sends an **empty-string** type, which `IntentFilter.matchData` rejects against every filter in existence — typed filters need a type match, typeless ones need null — so *no app on the phone* can appear in that dialog (its own log says `There is no proper activity`). Samsung users go through Share instead:
  - `action: SEND` + `mimeType: */*`, **no scheme** — the share sheet. A SEND intent carries no data URI (a scheme in this filter would kill it; safe because expo-dev-client's `appendScheme` only touches VIEW filters), and its file rides in `EXTRA_STREAM`, which RN's `Linking` cannot read — so `MgbaCoreModule` bridges it: `initialSharedFile` reads the launching intent (cold start) and `OnNewIntent` emits the `sharedFile` event (warm, singleTask), exported from the module as `sharedFiles: SharedFileSource` and passed via `AppConfig.sharedFiles` into the shared `useOpenedRom`. `*/*` rather than `application/*` because each file manager invents its own SEND fallback type and a share sheet is opt-in per gesture anyway.

  The cost of all this is being offered for any `application/*` or typeless file and appearing in every share sheet. That is fine because `importRomFromUri` rejects a non-ROM with the same `unsupported_file` copy the picker uses. `pathPattern` can't narrow either one: a `content://` URI carries no filename — `content://media/external/file/1000056541` is a real example — and its authority differs per file manager, so the two `file://` filters are a legacy path only. Their patterns are **double-escaped** (`".*\\\\.gba"` in JSON → `.*\\.gba` in the XML) because the manifest parser unescapes once before `PatternMatcher` sees the string; a single `\\` silently degrades `\.` to "any character". They repeat with an extra `.*\\.` because Android's glob doesn't backtrack, so one pattern misses any path with an earlier dot. Expo appends `exp+gba` to every generated filter's scheme set — harmless noise from the dev-client scheme mod, not something to remove.
- `App.tsx` builds the `AppConfig` — consoles `gba`/`gbc`/`gb`, `core` + `EmulatorView` from `./modules/mgba-core`, `licenseNotice` from `./license` — and renders the shared `<AppRoot />`.
- `license.ts` — the notice Settings → Legal → License shows, mirroring `docs/legal/license/license-mpl-gba.md`. **This app's notice is MPL 2.0, not GPL like the other two apps'** — mGBA is Mozilla-licensed. It also names blip_buf (LGPL 2.1), which `CMakeLists.txt` appends to `THIRD_PARTY_SRC` outside every feature guard, so it is statically linked into `libmgba-jni.so` on every build and cannot be dropped from the notice. If the mGBA pin ever moves off 0.10.5, the version stated in the notice moves with it.
- `modules/mgba-core/` — local Expo Module (Android/Kotlin/C++):
  - `android/vendor/mgba` — **git submodule** pinned to mGBA `0.10.5`. After a fresh clone run `git submodule update --init`. Keep the pin at 0.10.x: the JNI audio code uses the blip_buf API, which 0.11 replaces with `mAudioBuffer`.
  - `android/src/main/cpp/` — the JNI layer: `CMakeLists.txt` builds libmgba (static, `LIBMGBA_ONLY`, GBA+GB cores) plus the `mgba-jni` shared lib; `emulator_engine.cpp` is a singleton owning the mCore instance, a dedicated emulation thread (runFrame → audio pump → SurfaceView blit, clock-paced), the framebuffer, and the ANativeWindow; `audio_sink.cpp` is an Oboe output stream fed by an SPSC ring buffer. Never include mGBA headers outside the `mgba-jni` target — its `M_CORE_*` defines must match the lib's or struct layouts silently diverge.
  - `android/.../MgbaCoreModule.kt` — implements the `EmulatorCore` contract and owns the idle/running/paused state machine + events. Its `OnActivityEntersBackground`/`OnActivityEntersForeground` hooks auto-pause a running game (and resume it) around backgrounding and screen-off — the emu thread and Oboe stream are native, so JS-side `AppState` handling alone can't stop them — and the background hook also calls `nativeFlushSaves`, because a paused game runs no frames and frames are what normally flush the battery save. `OnDestroy` unloads as a last resort, since `unloadRom` is what commits the save.
  - `android/.../MgbaCoreNative.kt` — the JNI mirror; also maps contract button names → mGBA key bits.
  - `android/.../RomFiles.kt` — resolves ROM URIs (copies `content://` into cache) and keys battery saves/savestates by ROM SHA-1 under `filesDir/mgba/`; `deleteSaveData` matches states by `<sha1>.ss` prefix so no slot can be missed.
  - `android/.../MgbaCoreView.kt` — hosts the SurfaceView, aspect-fits it, and hands the Surface to the engine.
  - `src/index.ts` — typed wrapper exporting `core: EmulatorCore` and `EmulatorView`. Keep it in lockstep with the Kotlin definition and `@emulators/core-interface`.

### Saves

- **Never pass `SAVESTATE_SAVEDATA` when loading a state.** mGBA applies a state's embedded save either way; the flag only chooses between writing it straight over the real `.sav` (`GBASavedataLoad` — loading an old state would throw away newer in-game progress) and masking it read-only, which commits only if the game saves afterwards. The mask is upstream's default and the only correct behaviour here. Saving still uses `SAVEDATA | RTC | METADATA`.
- `forceSaveClean()` (in `emulator_engine.cpp`) drives mGBA's `GBASavedataClean`/`GBSramClean` age check by hand — two calls, the second past `mSAVEDATA_CLEANUP_THRESHOLD` — because that sync only happens on running frames. It runs on backgrounding and inside `unloadRom` before `deinit`, which msyncs the mapping but writes no RTC footer and drops a masked save's pending writeback.
- `captureScreenshot` goes engine → JNI (`nativeCaptureFrame` returns `[width, height, pixels...]`) → Kotlin `Bitmap` → PNG at a path JS chose. The framebuffer is RGBX with **red in the low byte** (what the blit hands `WINDOW_FORMAT_RGBX_8888`), so the JNI wrapper swaps red and blue for Android's ARGB ints — blue-tinted thumbnails mean that swizzle broke.
- Anything touching the core must go through `runOnEmuThread`, which runs the closure between frames and works while paused.

## Building

- The first native build compiles ~500 mGBA C files for 2 ABIs (arm64-v8a, x86_64) — expect several minutes cold.
- Gradle must run on **JDK 17–21** (e.g. Temurin 21 at `%LOCALAPPDATA%\Java\jdk-21.0.12+8` — set `JAVA_HOME` before building). JDK 24+/Android Studio JBR 25 breaks AGP's native-build tasks: the child JVM's "restricted method" native-access warning on stderr fails `configureCMake*`. The generated `android/local.properties` must point `sdk.dir` at the Android SDK.
